## Agenda Items

- [ ] Re-visit factoring out ocm-kit from community repository (vote?)
- [ ] Philipp and Jonas to follow-up on proposal PR towards community repo, introducing Python OCM language bindings
- [ ] SIG Runtime Project Board: Gergely and Philipp to follow-up on a written proposal which can be used for an async vote afterwards
- [ ] Ilja to follow-up on the Go vanity URLs for ocm-kit
  - Fabian (prep): Quickly looked into it, input for the discussion
    - Go vanity URLs would work, we already do this for the bindings (`ocm.software/open-component-model/...`)
    - e.g. `ocm.software/community/ocm-kit`, pointing to the `ocm-kit` subdirectory of the community repo (supported since Go 1.25)
    - If we move ocm-kit later, we only update the redirect, Go consumers don't notice
    - OCM has to own and keep hosting the vanity URL (lives on the ocm.software website), also if ocm-kit moves to its own org
    - Changing the module path is a one-time breaking change, cheap now while we are at v0.x
    - Does NOT help with the container image (`ghcr.io/open-component-model/community/ocm-kit`) and the cosign signing identity
      - Image name changes when moving to a different org, signing identity changes with any repository move
      - So consumers have to update image references and/or verification policies, this is the actual migration pain
  - Fabian: Rather not do this for community projects
    - OCM would have to own the URL forever, even if the project moves away or goes stale
    - `community/` in the path at least makes clear it's not OCM core
    - If ocm-kit is going to move, better do it now while at v0.x, or the project owns its own domain
