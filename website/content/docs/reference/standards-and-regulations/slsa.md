This page describes how the OCM release artifacts align with the
[SLSA](https://slsa.dev) (Supply-chain Levels for Software Artifacts) Build
track, as defined in [SLSA v1.2](https://slsa.dev/spec/v1.2/), the current
version. Every released CLI binary, OCI image, and Helm chart carries a GitHub
build provenance attestation. Since OCM 0.20.0, all of them are attested from a
reusable workflow, which is GitHub's recipe for Build Level 3, and the release
workflow verifies the signing workflow of each attestation before promoting a
release. OCM component versions are signed, not provenance-attested; this and
other gaps are documented below.

## SLSA Build Track Summary

SLSA organizes supply chain security into tracks and levels. The
[Build track](https://slsa.dev/spec/v1.2/build-track-basics) covers how an
artifact was built; its
[requirements](https://slsa.dev/spec/v1.2/build-requirements) are unchanged
from SLSA v1.0:

| Level | Name | What it requires |
| --- | --- | --- |
| Build L0 | No guarantees | Nothing |
| Build L1 | Provenance exists | The build produces provenance describing how the artifact was built |
| Build L2 | Hosted build platform | Provenance is signed and generated by a hosted build platform (e.g. GitHub Actions) |
| Build L3 | Hardened builds | Provenance is unforgeable: the signing key is inaccessible to user-defined build steps. Builds are isolated: ephemeral environments, no influence between builds, and no cache poisoning |

SLSA itself does not name GitHub workflows. GitHub maps its platform onto the
levels: artifact attestations
([docs](https://docs.github.com/en/actions/concepts/security/artifact-attestations))
provide Build L2, and attestations generated inside a
[reusable workflow](https://docs.github.com/en/actions/how-tos/reuse-automations/reuse-workflows)
provide
[Build L3](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/increase-security-rating),
because the provenance then names the reusable workflow as the signer, which
consumers can pin with `gh attestation verify --signer-workflow`. The levels
on this page follow GitHub's mapping.

## How OCM Generates Attestations

OCM uses
[`actions/attest-build-provenance`](https://github.com/actions/attest-build-provenance)
to create [in-toto](https://in-toto.io/) provenance attestations signed by
Sigstore through the GitHub Actions OIDC identity. The attestation is stored in
the repository's attestation ledger and, for OCI artifacts, also pushed to the
container registry alongside the image or chart.

The build is split across reusable workflows:

| Workflow | Trigger | Role |
| --- | --- | --- |
| `release.yml` | `workflow_dispatch` (release manager) | Top-level release orchestrator; calls `pipeline.yml` and `controller-chart-final.yml` |
| `pipeline.yml` | `push` / `pull_request` (daily CI) or `workflow_call` (from `release.yml`) | Calls `cli.yml` and `kubernetes-controller.yml` for builds, then publishes and attests images and the Helm chart |
| `cli.yml` | `workflow_call` only | Builds CLI binaries and attests them |
| `kubernetes-controller.yml` | `workflow_call` only | Builds the controller image (no attestation; attestation happens at publish time in `pipeline.yml`) |
| `controller-chart-final.yml` | `workflow_call` only | Re-packages, pushes and attests the final Helm chart during a release |

Under GitHub's mapping, the level depends on where the attestation is
generated. In a reusable workflow, the provenance names that workflow as the
signer, separate from the workflow that called it:

- **CLI binaries** are attested in `cli.yml`, which is always invoked as a
  reusable workflow.
- **CLI image, controller image, and Helm chart (RC)** are attested in
  `pipeline.yml`. On a release, `release.yml` calls `pipeline.yml` as a
  reusable workflow, so the attestation is generated with Build L3 isolation.
  On a direct push to `main`, `pipeline.yml` runs as the top-level workflow,
  so the same artifacts receive Build L2 attestations.
- **Final Helm chart** (the version-promoted chart published during a final
  release) is re-packaged and attested in `controller-chart-final.yml`, which
  `release.yml` calls as a reusable workflow. This attestation is Build L3.

## Per-Artifact Provenance

| Artifact | Registry path | Attested | Build level (release) | Build level (push to main) |
| --- | --- | --- | --- | --- |
| CLI binaries (`ocm-<os>-<arch>`) | GitHub release assets | ✅ `subject-path` | Build L3 | Build L3 |
| CLI OCI image | `ghcr.io/open-component-model/cli` | ✅ `subject-digest`, pushed to registry | Build L3 | Build L2 |
| Controller OCI image | `ghcr.io/open-component-model/kubernetes/controller` | ✅ `subject-digest`, pushed to registry | Build L3 | Build L2 |
| Helm chart (RC) | `ghcr.io/open-component-model/kubernetes/controller/chart` | ✅ `subject-digest`, pushed to registry | Build L3 | Build L2 |
| Helm chart (final) | `ghcr.io/open-component-model/kubernetes/controller/chart` | ✅ `subject-digest`, pushed to registry | Build L3 | — |
| OCM component versions | `ghcr.io/open-component-model//ocm.software/*` | ❌ No GitHub attestation | — | — |

The release workflow verifies every RC attestation before promoting the release
to final (job `verify_attestations` in `release.yml`), pinning the expected
signer workflow (`cli.yml` for binaries, `pipeline.yml` for images and the RC
chart). If an attestation is missing, invalid, or signed by another workflow,
the final release is not created.

## Verifying Attestations

Use the [GitHub CLI](https://cli.github.com/) `gh attestation verify`
subcommand. The examples below use `--owner open-component-model`; you can
narrow to `--repo open-component-model/open-component-model` instead.

### CLI Binaries

Download a release binary and verify it against the repository's attestation
ledger:

```shell
gh release download v0.20.0 \
  --repo open-component-model/open-component-model \
  --pattern "ocm-linux-amd64" \
  --dir /tmp/ocm

gh attestation verify /tmp/ocm/ocm-linux-amd64 \
  --owner open-component-model
```

### CLI OCI Image

```shell
gh attestation verify \
  oci://ghcr.io/open-component-model/cli:0.20.0 \
  --owner open-component-model
```

### Controller OCI Image

```shell
gh attestation verify \
  oci://ghcr.io/open-component-model/kubernetes/controller:0.20.0 \
  --owner open-component-model
```

### Helm Chart

```shell
gh attestation verify \
  oci://ghcr.io/open-component-model/kubernetes/controller/chart:0.20.0 \
  --owner open-component-model
```

To pin verification to the reusable build workflow (proving Build L3
provenance), add `--signer-workflow`. For the CLI image and RC chart, the
signer is `pipeline.yml`:

```shell
gh attestation verify \
  oci://ghcr.io/open-component-model/cli:0.20.0 \
  --owner open-component-model \
  --signer-workflow open-component-model/open-component-model/.github/workflows/pipeline.yml
```

For the final Helm chart, the signer is `controller-chart-final.yml`:

```shell
gh attestation verify \
  oci://ghcr.io/open-component-model/kubernetes/controller/chart:0.20.0 \
  --owner open-component-model \
  --signer-workflow open-component-model/open-component-model/.github/workflows/controller-chart-final.yml
```

For CLI binaries the signer workflow is `cli.yml`:

```shell
gh attestation verify /tmp/ocm/ocm-linux-amd64 \
  --owner open-component-model \
  --signer-workflow open-component-model/open-component-model/.github/workflows/cli.yml
```

### SBOM and OpenVEX Attestations

Besides build provenance, the release pipeline attests an SPDX SBOM to every CLI
binary and to both OCI images (one per platform), and attests the OpenVEX
document to every CLI binary and both OCI images. The images are scanned with
that same document. Select the attestations by predicate type:

```shell
# SBOM (SPDX 2.3) of an image
gh attestation verify oci://ghcr.io/open-component-model/cli:0.20.0 \
  --owner open-component-model \
  --predicate-type https://spdx.dev/Document/v2.3 \
  --format json --jq '.[].verificationResult.statement.predicate.name'

# OpenVEX of a binary, signed by pipeline.yml
gh attestation verify /tmp/ocm/ocm-linux-amd64 \
  --owner open-component-model \
  --predicate-type https://openvex.dev/ns/v0.2.0 \
  --signer-workflow open-component-model/open-component-model/.github/workflows/pipeline.yml \
  --format json --jq '.[].verificationResult.statement.predicate.statements'
```

SBOMs and VEX documents are not SLSA provenance; they are signed by the same
workflows and verified the same way. The release verifies the OpenVEX
attestation of every binary before promoting a release. The same documents are
also release assets and resources of the OCM component versions; see
[EU Cyber Resilience Act: SBOMs and VEX Documents]({{< relref "docs/reference/standards-and-regulations/cra.md#sboms-and-vex-documents" >}}).

## Permissions

The workflows that generate attestations require these token permissions:

| Permission | Purpose |
| --- | --- |
| `id-token: write` | Request a GitHub Actions OIDC token used as the Sigstore signing identity |
| `attestations: write` | Store the attestation in the repository's attestation ledger |
| `artifact-metadata: write` | Create the artifact metadata storage record when the attestation is pushed to a registry |
| `packages: write` | Push the attestation to the container registry (OCI artifacts only) |

These permissions are declared on the attesting jobs in `cli.yml`,
`pipeline.yml`, `release.yml` and `controller-chart-final.yml`, and are
forwarded to reusable workflows through the `permissions` block of the caller.

## Known Gaps

OCM does not claim SLSA certification or formal conformance. The following gaps
exist:

| Gap | Detail |
| --- | --- |
| Push-to-main images and chart are Build L2 | When `pipeline.yml` runs as a top-level workflow (push to `main`), it signs the image and chart attestations itself, which GitHub rates Build L2. Only release builds, where `release.yml` calls `pipeline.yml` as a reusable workflow, reach Build L3. CLI binaries are attested in the reusable `cli.yml` on every non-PR build. |
| Shared Go build cache | SLSA Build L3 requires that one build cannot inject entries into a cache another build uses. `cli.yml` uses `actions/setup-go` with its default Go build cache, so release builds restore caches written by earlier default-branch builds. Pull requests from forks cannot write those caches, and Go's build cache is keyed by input hashes, but the cache is still shared between builds. Release builds without the cache would close this. |
| Image provenance is signed in the publish job | The images are built in `cli.yml` and `kubernetes-controller.yml` and passed as workflow artifacts to the `publish_*` jobs of `pipeline.yml`, which push and attest them. The provenance therefore describes the `pipeline.yml` run as a whole, not the individual build job. |
| OCM component versions have no GitHub attestation | OCM component versions (`ocm.software/ocm`, `ocm.software/cli`, `ocm.software/kubernetes/controller`) are signed with keyless Sigstore through the OCM CLI's signing handler, not attested with `actions/attest-build-provenance`. Sigstore signatures tie the component version to a GitHub Actions OIDC identity but are not SLSA Build provenance. |
| SLSA Source track not assessed | SLSA v1.2 adds a [Source track](https://slsa.dev/spec/v1.2/source-requirements) for the integrity of the source revision. OCM has not assessed it, and the repository settings it depends on, such as branch protection, are not visible in the repository content. |

Report supply-chain-related problems or gaps as
[GitHub issues](https://github.com/open-component-model/open-component-model/issues).
