Component Version Storage

OCM has no storage format of its own. It is designed to store component versions in established content-addressable storage technologies. Currently, the only supported technology is OCI.

Component versions live in OCI registries, or in a Common Transport Format (CTF) archive, OCM’s file system representation of an OCI registry.

This page explains how a component version and its local blobs map to OCI artifacts, what you see in a registry after ocm add cv or ocm transfer cv, and why an embedded image can be pulled with docker, oras, or crane.

Terminology: OCM and OCI terms on this page

OCM and OCI use some of the same words for different things. This page prefixes OCI terms with OCI wherever they could be confused. Terms without a prefix are OCM terms, so descriptor on its own always means the component descriptor.

TermModelMeaning
Component versionOCMA versioned component. Stored as one OCI manifest or one OCI index.
Component descriptorOCMThe document that describes a component version: its resources, references, and how to access them. Not an OCI descriptor.
Local blobOCMA resource stored by value, next to the component descriptor. Stored as one OCI layer, or as a whole OCI artifact.
OCM repositoryOCMWhere component versions are stored: an OCI registry plus an optional path, or a CTF archive. Holds many components.
OCI repositoryOCIOne named repository inside an OCI registry. OCM uses one per component, holding all of its versions.
OCI descriptorOCIA reference to content by mediaType, digest, and size, as used in a manifest’s config and layers.
OCI manifestOCIOne OCI config plus a list of OCI layers, for example one platform of an image.
OCI indexOCIA list of OCI manifests or further OCI indexes, for example a multi-platform image. The CTF’s artifact-index.json is not one.
OCI layer, OCI configOCIThe content an OCI manifest references, each addressed by an OCI descriptor.
OCI artifactOCIAn OCI manifest or OCI index together with everything it references.
OCI imageOCIAn OCI artifact that holds a container image: an OCI manifest for one platform, or an OCI index for several.

Why Store Component Versions as OCI Artifacts?#

  • Reuse existing infrastructure: Most teams that ship containers already operate an OCI registry, with access control, replication, and garbage collection. Storing component versions there means no extra storage backend.
  • Content addressing: OCI identifies every layer, manifest, and index by its digest. OCM uses those digests as the localReference of a local blob, so storage, deduplication, and integrity checks come for free.
  • Native consumption: OCI artifacts stored by value keep their OCI shape. Tools that know nothing about OCM can consume them directly.

How It Works#

A component version is stored as an OCI artifact that carries the component descriptor and every resource stored by value (a local blob). It takes one of two forms, depending on the local blobs. OCM picks the form the content needs, and readers accept both.

Manifest

Used when no local blob is an OCI artifact. The tag points directly to the component descriptor’s OCI manifest. Its OCI layers are the component descriptor and one layer per local blob, and its OCI config points to the component descriptor layer.

Index

Used as soon as one local blob is an OCI artifact: an image, a Helm chart, or any OCI image layout. The tag points to an OCI index. Its first entry is the component descriptor’s OCI manifest, marked by the artifact type application/vnd.ocm.software.component-descriptor.v2. Every further entry is the OCI manifest or OCI index of an embedded OCI artifact. Local blobs that are plain files stay OCI layers of the component descriptor’s OCI manifest.

In both forms, the component descriptor points to a local blob the same way: localReference is the digest of the OCI layer, OCI manifest, or OCI index that holds the content.

Repository and Version Mapping#

The location of a component version follows from three things: the OCM repository, the component name, and the version. An OCM repository in a registry is a registry host with an optional path below it, for example ghcr.io/acme/ocm (baseUrl and subPath of an OCIRepository/v1). Each component gets its own OCI repository below that path, and each component version is a tag in it:

For example, github.com/acme.org/demo in version 1.0.0 in ghcr.io/acme/ocm is stored at ghcr.io/acme/ocm/component-descriptors/github.com/acme.org/demo:1.0.0. All versions of a component, and all local blobs of those versions, live in this one OCI repository.

Two Shapes of Local Blob#

How OCM stores a local blob depends on its content:

ContentStored aslocalReference is the digest ofmediaType in the access
Plain file, directory archive, Git snapshot, …One OCI layer, listed in the component descriptor’s OCI manifestthe OCI layerthe content’s media type, e.g. text/plain
OCI artifact: an OCI image layout added with File/v1, a chart added with Helm/v1, or an image copied by value during transferIts full graph of OCI manifests and OCI indexes, unpacked into the OCI repositorythe root OCI manifest or OCI indexapplication/vnd.oci.image.index.v1+json or …manifest.v1+json

OCM does not store the file an OCI artifact was added from, such as an OCI image layout archive. It unpacks the file and stores every OCI index, OCI manifest, OCI config, and OCI layer in it as a separate blob in the OCI repository. Nothing is changed or re-created, so the image keeps its original digest.

Storage in a CTF Archive#

OCM’s Common Transport Format (CTF) is not an OCI standard. OCM defines it so that component versions can travel without an OCI registry, as a directory or a TAR archive, for example into an air-gapped environment. It is also not an OCI image layout: instead of index.json and oci-layout, it has its own artifact-index.json that maps OCI repositories and tags to digests, the way a registry does. Despite its name, artifact-index.json is not an OCI index. The blobs the CTF stores are the same OCI manifests, OCI indexes, OCI configs, and OCI layers as in a registry:

artifact-index.json lists every OCI manifest and OCI index with its OCI repository, and the tag for the component version itself. Because the content is identical, transferring a CTF to a registry copies the graph and keeps every digest, including localReference values and the digests signatures cover.

Key Properties#

PropertyDescription
OCI-nativeA component version is a plain OCI artifact; any conformant registry stores it, and any OCI tool can inspect it.
One graph, two backendsRegistries and CTF archives hold the identical graph, so moving between them preserves every digest.
Content-addressed local blobslocalReference is the digest of the stored OCI layer, OCI manifest, or OCI index — stable across OCM repositories.
Self-containedAll local blobs live in the component’s own OCI repository, next to the component descriptor that references them.
Native artifacts stay nativeOCI artifacts stored by value keep their structure and digest and are pullable by digest.

Relationship to Other Concepts#

  • Transfer and Transport — Transfer with a local blob uploader converts external OCI references into local blobs in this format.
  • Resource Repositories — Resources stored by reference stay in external repositories; this page covers what is stored by value.
  • Signing and Verification — Resource digests and localReference values are content addresses in this graph, which is why a faithful copy keeps signatures valid.
  • Component Identity — The component name and version determine the OCI repository and tag.

When This Matters#

  • You inspect a registry or CTF archive and want to understand the OCI manifests, OCI indexes, and tags you see.
  • You want to deploy an image embedded in a component version without the OCM CLI, e.g. from a Pod spec.
  • You migrate from OCM v1 and need to know why older embedded images are not pullable.

If you only add, transfer, and download component versions with OCM commands, OCM handles this layout for you.

OCM v1 and OCM v2#

This page describes the OCM v2 format. OCM v1 stored component versions differently. OCM v2 reads component versions that OCM v1 created, but when you work with such content, the differences matter.

OCM v1OCM v2
Component versionAlways a single OCI manifestAn OCI manifest, or an OCI index once it embeds OCI artifacts
Embedded OCI artifactPacked into an artifact set — a .tar.gz of the image — stored as one opaque OCI layerUnpacked into a native graph of OCI manifests and OCI indexes
Local blob media typeapplication/vnd.oci.image.manifest.v1+tar+gzip (or …index.v1+tar+gzip)application/vnd.oci.image.manifest.v1+json (or …index.v1+json)
localReferenceDigest of the archiveDigest of the image’s root OCI manifest or OCI index
Pull with docker/oras/crane or reference from a PodNot possible: the registry sees an archive, not an imagePossible by digest

A v1 artifact set remains an OCI layer when it is copied by value, because unpacking it would change its localReference and the digests a signature covers. To make such an image pullable, upload it as a standalone OCI image with an OCI uploader during transfer.

In the other direction, the OCM v1 CLI reads local blobs stored in the v2 format starting with v0.36.0. Older v1 releases cannot access them.
