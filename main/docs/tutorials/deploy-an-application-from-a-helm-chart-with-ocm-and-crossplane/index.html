Deploy an Application from a Helm Chart with OCM and Crossplane

What You’ll Learn#

Your application ships as a Helm chart, and you want its delivery to be repeatable: one versioned OCM component that carries the chart, its container image, and the instructions to deploy it, with image references that localize themselves as the component moves between registries. This tutorial builds that deployment on Crossplane, using a CompositeResourceDefinition (XRD) plus a Composition to reconcile the deployment graph. The XRD registers the Bootstrap schema, and the Composition creates the OCM and GitOps deployer objects (Flux or Argo CD) directly. We will use Podinfo as the example application.

Coming from the kro tutorial?

This tutorial reaches the same end state as Deploy an Application from a Helm Chart with OCM and kro, swapping kro’s ResourceGraphDefinition for a Crossplane XRD + Composition. Reading the kro tutorial first is not required.

By the end, you’ll have:

  • An OCM component containing a Helm chart, an image reference, and a Crossplane XRD + Composition
  • A running Podinfo application deployed by applying the Bootstrap composite resource
  • Understanding of how localization keeps image references in sync after transfers

Prerequisites#

Set up your environment

Before starting, make sure you have set up your environment as described in the setup guide.

  • Controller environment with OCM Controllers installed
  • Crossplane installed as the orchestrator, following Set up Controller Environments > Install an Orchestrator (the Crossplane tab)
  • A GitOps deployer installed, either Flux or Argo CD, following Set up Controller Environments > Install a Deployer. Crossplane composes that deployer’s objects directly: the Flux OCIRepository and HelmRelease, or the Argo CD Application. The matching controllers must be running (Flux’s source-controller and helm-controller, or Argo CD’s application-controller). For Argo CD, apply the Bootstrap in the argocd namespace (via BOOTSTRAP_NAMESPACE, see Environment Setup), so no extra Argo CD configuration is needed: the composed Application lands where stock Argo CD already watches.
  • Custom RBAC with both Crossplane grants, which live in two separate places in that guide:
    • The Crossplane tab under Create a ClusterRole and ClusterRoleBinding gives the OCM controller read access (get, list, watch) on compositions and compositeresourcedefinitions (apiextensions.crossplane.io) so it can check the deployed objects for drift. The bootstrap-deployer service account gets its own write access from the ClusterRole in bootstrap.yaml later in this tutorial.
    • The Crossplane subsection under RBAC for the orchestrator’s own service account lets Crossplane’s own service account compose the OCM Resource and the deployer objects (Flux or Argo CD).
  • The Patch and Transform function (function-patch-and-transform), which the Composition runs as its pipeline step. Install it via the Crossplane tab of Set up Controller Environments > Install an Orchestrator.
  • OCM CLI installed
  • Access to an OCI registry (e.g., ghcr.io)
  • envsubst installed (pre-installed on most Linux/macOS systems as part of gettext)
Private registries

If using a private registry, you’ll need to configure credentials for both the OCM CLI and the controller resources. See Configure Credentials for Controllers for details.

Concepts#

The Bootstrap Pattern#

Instead of applying the deployment graph (the XRD + Composition) to the cluster by hand, the bootstrap pattern packages that graph as a resource inside the OCM component. The OCM Deployer controller then extracts the blob from the component and applies it for you. The deployment instructions travel with the component and stay versioned alongside the chart and image, so every environment installs the same graph. In this tutorial the packaged blob is a Crossplane XRD + Composition.

How the Pieces Fit Together#

The graph engine is what reconciles the deployment graph and creates the deployer objects. This tutorial ships a Crossplane CompositeResourceDefinition (XRD) plus a Composition. The XRD registers a Bootstrap composite kind. When you apply a Bootstrap resource, Crossplane resolves the chart and image through OCM Resource objects, then composes the deployer objects directly: for Flux an OCIRepository and a HelmRelease, for Argo CD a single Application. The deployer then renders the chart into the running workload.

The OCM Resource and the deployer objects are composed directly by the Composition, with no intermediate wrapper.

If you already know the kro variant, the building blocks map like this (otherwise skip the table):

kroCrossplane
ResourceGraphDefinitionCompositeResourceDefinition (XRD) + Composition
Schema kind: Bootstrap registered by kroComposite kind: Bootstrap registered by the XRD
Instance of the Bootstrap CRDA Bootstrap composite resource
kro reconciles the graphCrossplane reconciles the composite, creating the composed resources

The Composition runs in pipeline mode (mode: Pipeline). A single pipeline step invokes the function-patch-and-transform function, whose input holds the patch-and-transform resource list. The resolved chart and image OCI coordinates travel from the OCM Resource objects to the deployer objects through the composite’s status.atProvider fields, since patch-and-transform wires values only between a composed resource and the composite, never directly between two composed resources.

Localization#

Localization keeps image references in sync when a component moves between registries. Transferring the component rewrites the image references in its descriptor to point at the target registry. At deploy time the Composition reads the resolved OCM Resource status and injects the current image into the Helm values, so the workload always runs the image from the registry it was transferred to, not the original upstream location.

Troubleshooting#

Authentication Errors (401 Unauthorized)#

If you see 401: unauthorized errors, your GitHub package is private. Either:

  • Make the package public in GitHub Package settings
  • Configure credentials as described in the “Define the component” step

XRD or Composition Not Installing#

Check controller logs:

Common causes: missing component, wrong repository URL, credential issues, or an RBAC gap. The bootstrap-deployer service account needs write access to apply the XRD and Composition, and the controller needs read access to watch them for drift. See RBAC Permission Errors below.

RBAC Permission Errors#

The NamespacedDeployer applies the XRD and Composition as its bootstrap-deployer service account, while the controller only watches them with its own identity. A forbidden error can come from either side:

  • If the deployer logs show cannot create resource, the bootstrap-deployer service account lacks write access. It gets that from the bootstrap-deployer ClusterRole and binding in bootstrap.yaml. Confirm the grant with:

  • If the controller logs show it cannot list or cannot watch the XRD and Composition, the controller lacks read access. Apply the ocm-controller-crossplane ClusterRole and binding from Configure Custom RBAC for Deployers (select the Crossplane tab), then confirm the grant with:

Separately, if the composite’s composed resources stay stuck (see Composite Not Becoming Ready), the fault is Crossplane’s own service account. Crossplane composes the OCM Resource and the deployer objects directly, so Crossplane core must be granted access to those non-Crossplane kinds. See the next section.

Composed resources stay forbidden#

Crossplane’s service account can create any resource installed by a provider or defined by an XRD, but it must be granted access to compose any other kind of resource (the OCM Resource and the deployer objects here). Without that grant the composite reports a forbidden error, for example

Grant Crossplane’s service account access to the composed kinds with an aggregated ClusterRole, as described in Configure Custom RBAC for Deployers > Crossplane.

Composite Not Becoming Ready#

If the Bootstrap composite stays SYNCED=False or READY=False:

Inspect the composed resources directly to see which one is stuck:

Check the Events section and each composed resource’s status for error messages. A common cause is Crossplane lacking RBAC for the composed OCM Resource or the deployer CRDs (see Composed resources stay forbidden).

ImagePullBackOff Errors#

If pods show ImagePullBackOff or ErrImagePull errors, the kubelet cannot pull the localized image from your private registry. Set image.pullSecrets (for example image.pullSecrets: [{name: ghcr-secret}]) in the chart values of the Composition’s deployer resource: the Flux helmrelease spec.values, or the Argo CD application spec.source.helm.valuesObject. Podinfo reads pull secrets from image.pullSecrets, a top-level imagePullSecrets value is ignored.

What You Learned#

You’ve successfully:

  • Created an OCM component with an embedded Crossplane XRD + Composition
  • Configured an OCI uploader in .ocmconfig to enable localization during transfer
  • Deployed the component by applying a Bootstrap composite, letting Crossplane compose the deployer objects directly
  • Verified that localization kept image references in sync

This pattern lets developers ship deployment instructions alongside their software while operators only apply a simple composite, with Crossplane, rather than kro, reconciling the graph.
