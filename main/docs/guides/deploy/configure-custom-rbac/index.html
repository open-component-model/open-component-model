Configure Custom RBAC

The OCM Kubernetes Controller Toolkit ships with the minimum RBAC permissions needed to manage its own custom resources (Repository, Component, Resource, Deployer, NamespacedDeployer). It does not include permissions for the objects your deployers create, such as kro ResourceGraphDefinitions. You grant those yourself, and who needs which verbs depends on the deployer kind:

Deployer kindWrite verbs (create, update, patch, delete)Read verbs (get, list, watch)
NamespacedDeployerIts service accountThe controller’s service account
DeployerThe controller’s service accountThe controller’s service account

Prerequisites#

This guide assumes that you are already familiar with the concepts described in the following documents:

  • Concept: OCM controllers - OCM Controllers
  • Concept: Kubernetes Deployer - Deployer and NamespacedDeployer
  • An orchestrator installed, kro or Crossplane

When is this needed?#

The deployers use server-side apply to create and manage the objects in the deployed resource, and the controller watches those objects for drift. Every kind a deployer creates needs RBAC, custom resources and standard Kubernetes resources alike. Common examples:

  • kro ResourceGraphDefinitions (kro.run)
  • Crossplane CompositeResourceDefinitions and Compositions (apiextensions.crossplane.io)
  • Deployments (apps) and Services (core)
  • Any other resource type your deployers create

NamespacedDeployer: grant the service account#

A NamespacedDeployer does not apply with the controller’s permissions. It impersonates the service account in spec.serviceAccountName, so write access goes to it through a Role and RoleBinding in the deployer’s namespace. Without spec.serviceAccountName it impersonates the default service account of its namespace, which you grant in the same way. Prefer a dedicated service account, as every pod in the namespace that names none runs as default.

Bind the service account by name. The controller impersonates only the user name, so bindings to groups such as system:serviceaccounts:my-team do not apply.

For objects in another namespace, create the Role and RoleBinding in that namespace instead. The subject keeps the service account’s own namespace (my-team), and the deployer gets access to shared-services only:

Only cluster-scoped kinds such as kro ResourceGraphDefinitions need a ClusterRole with a ClusterRoleBinding. Grant only the kinds the deployment needs.

Keep these permissions until the NamespacedDeployer is deleted. It prunes with them. Without them its deletion waits with a DeletionFailed condition until you restore them, and without the service account itself it orphans cluster-scoped and cross-namespace objects.

Grant the controller read access#

The controller watches deployed objects for drift with its own identity, for both deployer kinds. Create a ClusterRole with get, list and watch on every kind your deployers deploy, then bind it to the controller’s service account.

The service account name depends on the Helm release name

Least Privilege

Follow the principle of least privilege. Only grant the verbs and resources your deployers actually need.

RBAC for the orchestrator’s own service account#

Everything above grants RBAC to the OCM controller’s ServiceAccount. The orchestrator reconciles the graph with its own ServiceAccount, which is a second, separate RBAC concern.

kro#

If your Deployer targets a kro ResourceGraphDefinition (RGD), kro reconciles the graph with kro’s own ServiceAccount.

An RGD can define a brand-new schema-based kind (for example, a Podinfo or Bootstrap kind). In kro’s least-privilege aggregation mode, creating and managing instances of that kind, or any other object the RGD templates, requires extra RBAC for kro’s own ServiceAccount. The setup guide installs kro in this mode and already creates such roles for the OCM resources and for the Flux or ArgoCD resources.

Create a ClusterRole scoped to the kinds your RGDs create and manage, and label it rbac.kro.run/aggregate-to-controller: "true". In aggregation mode kro picks up every ClusterRole with this label, so you do not need a binding. See kro’s access control guide. Crossplane#

If your Deployer targets a Crossplane CompositeResourceDefinition (XRD) plus a Composition, Crossplane reconciles the composite with its own ServiceAccount (crossplane in crossplane-system). Crossplane’s service account can already create any resource installed by a provider or defined by an XRD, but you must grant it access to compose any other kind of resource. On a hardened cluster this is required before the composite can create its composed resources.

For the bootstrap pattern Crossplane composes the two OCM Resource objects (the chart and the image) and the deployer objects. For Flux those are ocirepositories.source.toolkit.fluxcd.io and helmreleases.helm.toolkit.fluxcd.io. For Argo CD it is applications.argoproj.io. Grant them with a ClusterRole that aggregates to Crossplane’s primary role. The rbac.crossplane.io/aggregate-to-crossplane: "true" label is what wires it into Crossplane’s service account:

The aggregation label is critical: without it the role is never folded into Crossplane’s service account. Confirm the grant propagated:
